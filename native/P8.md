# P8 原生编曲与语义 JSON

当前目标和范围见 [AGENTS.md](../AGENTS.md)，具名回归结果见 [覆盖清单](../docs/COVERAGE.md#p8-验收)。本文件说明接口、数据格式和实现。

## 请求与提交

`gp_create_from_spec` 从宿主模板新建文档。`gp_apply_spec`、`gp_import_json`、`gp_insert_tab`、`gp_edit_chord`、`gp_edit_lyrics`、`gp_edit_section` 和 `gp_presentation` 的 `page_metadata` 写入均返回 `request`，通过 `gp_operation` 查询终态。新建成功为 `created`，编辑成功为 `applied` 或 `unchanged`，失败为 `error`。详细读回在 `result`，新建的批量提交结果在 `spec_result`；文档集合也返回最近的 `editing` 请求。历史保留最近 64 个已归档请求。

请求绑定发起时的文档 ID，依次在 Qt 主线程执行。等待中的请求阻止其他客户端写入；`gp_cancel` 只能取消尚未开始的批量编辑。进入原生提交后不抢占命令。`outcome_unknown=true` 时保留写入阻塞；`gp_recover` 比较实际模型与提交前、预期状态，返回 `applied`、`not_applied` 或仍未知。恢复不重放批量命令、不猜测撤销成功。

实现使用 GPCore 的 `Score::copyFrom` 构建独立原生副本，逐字段核对输入，最后通过 `Score::replaceScore` 一次提交。失败的副本不进入实时文档。宿主负责撤销历史、模型通知和未保存状态；一次 Undo 恢复提交前模型，Undo 后的 dirty 状态遵循宿主行为。构建新文档的规格在打开模板标签前已经完成原生预检。

## 最小建谱例子

调用 `gp_create_from_spec`：

```json
{
  "template": "Steel Guitar",
  "spec": {
    "metadata": {"Title": "Riff", "Music": "Composer"},
    "master_bars": [{"time_signature": {"numerator": 4, "denominator": 4}}],
    "tempo_points": [{"bar": 0, "position": 0, "value": 100, "unit": "Quarter"}],
    "tracks": [{
      "name": "Guitar",
      "template": "Steel Guitar",
      "staves": [{
        "tuning": [40, 45, 50, 55, 59, 64],
        "bars": [{"voices": [{"beats": [
          {"denominator": 4, "notes": [{"string": 0, "fret": 0}]},
          {"denominator": 4, "notes": [{"string": 0, "fret": 2}]},
          {"denominator": 4, "notes": [{"string": 0, "fret": 2}]},
          {"denominator": 4, "notes": []}
        ]}]}]
      }]
    }]
  }
}
```

模板名称来自 `gp_templates`。简单 riff 可调用 `gp_insert_tab`，如 `{"document":"…","track":0,"string":0,"text":"0-2-2-r|3-5","mode":"append"}`。`r` 是休止，`|` 分小节，默认八分音符，可用 `denominator` 改变时值。文本接口只表达单弦逐拍输入。

## guitarpromcp.p8 v1

`gp_export_json` 返回 `spec`；`gp_import_json` 接受此对象或其 JSON 字符串。导出固定包含 `schema:"guitarpromcp.p8"` 和 `version:1`，手写规格可同时省略两项。嵌套 MCP schema 由 `semanticSpecSchema()` 提供，结构预检和实际原生读回共同决定是否可提交。

所有数组位置、音轨、谱表、声部、小节、节拍及弦索引从 0 开始。弦按低音到高音排列。每个谱表的 `bars` 数量必须等于 `master_bars` 数量；`voices:[]` 或 `beats:[]` 表示空内容。导出保留四个声部的位置，省略宿主占位拍，不虚构休止。

| 对象 | 字段与含义 |
| --- | --- |
| 顶层 | `metadata`、`page_metadata`、`master_bars`、`tempo_points`、`tracks` |
| metadata | 宿主 `ScoreProperty` 名称，如 `Title`、`Subtitle`、`Artist`、`Album`、`Words`、`Music`、`Copyright`；完整名称可从导出读回 |
| track | `name`、`short_name`、`instrument_type`、`transposition`、`staves`；输入可用 `template` 和 `source_track` 选择模板中的音轨，也可复用目标已有音轨 |
| staff | `bars`；弦乐另外包含 `tuning`、`capo`、`partial_capo`、`partial_capo_strings`。键盘和鼓组不输出或接受弦乐调弦字段 |
| beat | `denominator` 为 1/2/4/8/16/32/64/128，`dots` 为 0..2；`rest` 必须与空 `notes` 一致；还可有 `tuplets`、`effects`、`legato`、`text`、`lyrics`、`chord` |
| note | 弦乐按 `string` 和 `fret` 写入，品位为 0..36；键盘和鼓组按 `midi` 写入。`midi`、`sounding_midi`、`accidental` 的导出值用于核对原生结果；不搜索替代指法或自动改写音高 |
| tuplets | `primary`、`secondary` 两层，启用对象为 `{"enabled":true,"actual":3,"normal":2}`，关闭为 `{"enabled":false}`；比例为 1..255 |
| connections | 音符 `tie` 和节拍 `legato` 含 `origin`、`destination`；tie 的 destination 连接前一拍，legato 的 origin 连接后一拍，可跨小节 |
| effects | 使用 `gp_read_bars` 的原生规范字段。音符覆盖弯音、滑音、泛音、震音、重音、指法及已有布尔技法；节拍覆盖拨弦、扫弦、摇把等已有字段。滑音 JSON 使用 `slide.flags`，其余派生端点从原生读回核对 |
| master bar | `time_signature`、`key_signature`、`repeat_start`、`repeat_end`、`repeat_count`、`alternate_endings`、`directions`、`double_bar`、`free_time`、`section`；跳转 ID 为 `gp_read_master_bars` 的 0..18 |
| tempo point | `bar`、`position`（小节中的比例，0 ≤ x < 1）、`value`（1..400）、`unit`、`linear`、`label`；音符单位来自 `gp_score.tempo.units` |

同拍音符按弦或 MIDI 身份核对，输入音符顺序不决定技法的目标。默认时值为四分音符、零附点；不自动补齐或量化未填满的小节。字段不合法、目标不匹配或原生读回未采纳输入时拒绝提交。

`replace` 重建音轨、谱表声部内容和小节数量；未给出的元数据、主小节属性沿用原模型，音轨配置沿用所选模板或原音轨。显式给出的 `tempo_points` 替换速度点。需要完全确定结果时使用导出的完整规格，显式清空反复、跳转或段落等字段。

`append` 在曲尾、`insert` 在 `bar` 前增加全局小节，规格中的小节和速度位置从插入内容的 0 开始。两种模式要求现有轨数、谱表数和乐器兼容；若提供已有音轨、调弦、转调或页面属性，它们必须与目标相同。`gp_insert_tab` 的 `replace` 仅替换指定声部的小节范围，新增小节的模式会顺移全曲。

限制为 32 轨、每轨 1..2 谱表、256 个主小节、每小节最多四声部、全曲 20000 拍；HTTP 请求另有 1 MiB 上限。JSON 表达本接口覆盖的曲谱语义，不是完整 GP 文件备份：任意音色/效果定义、自动化类别、所有歌词排版/连字符样式和任意刻谱样式不包含在 v1 中。无法按当前模型原样表示的组合会在预检或读回核对时报错；完整文件交换使用 GP 保存工具。

## 和弦、歌词和段落

和弦符号独立于实际 `notes`。`gp_edit_chord` 的 `chord` 支持 `root`、`bass`、`name`、原生 `type`（0..28，选项来自 `gp_read_chords.types`），或显式 `degrees:[{value,alteration,omitted}]`。音程名称沿用原生读回。`inversion`、`type_name` 是派生核对值；低音由 `bass` 写入。`operation:"remove"` 清除指定拍的和弦符号。

`diagram.frets` 是各弦绝对品位，-1 表示不发声，0 为空弦；`first_fret` 从 1 开始。`fret_count` 默认 5，`fingers:[{string,fret,finger}]` 的 fret 是图内相对品位。finger 为 0 拇指、1 食指、2 中指、3 无名指、4 小指。`barres:[{from_string,to_string,fret,finger}]` 使用相同图内坐标，finger 默认 1；宿主通过横按两端的重复指法位置持久化，导出 `fingers` 会包含这些端点。相冲突的指法会被拒绝。

`gp_edit_lyrics` 必须指定 `track/staff/bar/voice/beat`、`line:0..4` 和 `text`。一次设置一个精确位置的文本片段，空格、连字符和中文原样保留；空字符串清除该行。批量规格的 `lyrics` 数组使用同样的 `{line,text}`。它不做跨拍自动分词；客户端可以明确分配各拍音节。

`gp_edit_section` 在 `bar` 写入 `name`、`text`，或通过 `operation:"remove"` 清除起点。名称可用 Intro、Verse、Chorus、Bridge、Solo、Outro、Coda 等任意有效文本。`gp_read_sections` 返回起止小节；结束位置是下一段落之前或曲谱末尾。跳转记号由主小节 `directions` 表达，Coda 名称本身不添加播放跳转。

`gp_structure` 汇总元数据、音轨、主小节、段落和速度点。`gp_export_tab` 按小节和声部输出 ASCII，标明 MIDI 调弦、变调夹和时值，附带原生节拍数据及 `unrepresented` 清单。ASCII 不可逆，不承担连音、延音链和完整技法编码。

## 页面元数据

`gp_presentation` 的 `operation:"set"` 可设置一组 `page_metadata`：

```json
{
  "title": "Song",
  "author": "Artist",
  "composer": "Composer",
  "copyright": "Copyright 2026",
  "even_header": {"text": "%TITLE% — %PAGE%", "visibility": 0},
  "odd_header": {"text": "%TITLE% — %PAGE%", "visibility": 0},
  "first_footer": {"text": "First page footer", "visibility": 0},
  "first_page_number": {"text": "%PAGE%/%PAGES%", "visibility": 0}
}
```

页脚支持 `first_footer/even_footer/odd_footer`，页码支持 `first_page_number/even_page_number/odd_page_number`，对象可单独写 `text` 或 `visibility`。0 为可见、1 为隐藏、2 为折叠。首页标题使用 `title`；其他页头使用 `even_header/odd_header`。宿主处理 `%TITLE%`、`%ARTIST%`、`%PAGE%`、`%PAGES%` 占位符。

这些字段进入原生 `ScoreProperty` 和 `style::Stylesheet`，随 GP 文件保存；不会改变应用全局偏好。JSON spec 的 `page_metadata` 仅包含页面样式字段，标题等值统一放在 `metadata`，避免重复。其他页面尺寸和视图行为仍按 [原生 API 参考](API.md) 执行。

## 开发验证

```powershell
$env:GPMCP_DEVELOPMENT = '1'
./start-plugin.ps1 -Exe C:/隔离宿主/GuitarPro.exe -ScorePath ./artifacts/native-test.gp
./native/test-p8.ps1 -SessionFile ./.cache/native-session.json -RenderPdf
```

`-RenderPdf` 使用 Poppler 的 `pdftotext/pdftoppm`；已有 Python+pypdf 的环境也可通过 `-PdfTextPython` 提供 PDF 文本提取，Python 仅用于开发验证。普通构建可用 `-SkipFaults` 跳过开发故障注入，报告会明确标记。`test-all.ps1` 已包含 P8；开发模式还会验证提交前/后异常、等待期间的第二客户端阻塞、取消与观察恢复。

ABI 绑定既有宿主哈希。新增原生 `Score` 大小 0x1E8，`Chord` 为 0x50，`Diagram` 为 0x80，`Fingering` 为 16，`LyricsElement` 为 0x40，`AMPainting::FormattedText` 为 0x20；均有布局核验和静态断言。`AMPainting.dll` 另做哈希检查。没有引入新的进程、文件生成器或常驻运行时。
